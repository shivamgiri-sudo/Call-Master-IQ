Call Master — Full Design Specification

Org-level multi-process quality intelligence · call-master-backend integration · 6 personas

Tech Stack & Architecture Decisions

Backend

New route modules added to existing call-master-backend (TypeScript/Express). New folder src/callmaster/ with routes, services, repositories per persona. Shares existing DB pools + JWT middleware.

TypeScriptExpress 5 mysql2/promiseJWT

Frontend

Multi-file vanilla JS served from public/callmaster/. Single shell HTML + separated page JS files per persona. No build step. Same OLED dark theme as Finnable. ApexCharts via CDN.

Vanilla JSApexCharts OLED DarkInter + JetBrains Mono

Data Layer

Process-agnostic repository pattern. Each process (Outbound/Inbound/Chat/Email) has its own repo class that reads from its DB/table. A ProcessRegistry config maps process_id → DB pool → table → parameter schema.

Authentication & Access Control

Login → Role → Scope → JWT

Username + Password → cmAuth validates → JWT issued with role + branch_ids + process_ids → Frontend loads persona view
Admin
All access · impersonate roles · manage users · configure processes
CEO
All branches · all processes · summary only · no call-level detail
T&Q Head
All processes · analyst-level detail · no PII masking bypass
Branch Manager
Own branch_ids only · all processes in branch · no cross-branch
Process Manager
Assigned process_ids only · call-level detail · evidence + transcripts within own process · can manage analysts in their process
Analyst
Own data only · own calls/chats/emails · own scores · own coaching notes · no peer data

Data Layer Architecture

ProcessRegistry — Core Config Object

A single config file maps every process to its data source. When schemas arrive, only this file and the corresponding repo need updating — all services and routes stay unchanged.

// src/callmaster/config/processRegistry.ts
process_id: 'outbound'
  dbPool: externalPool
  table: 'CallDetails'
  agentCol: 'AgentName'
  dateCol: 'CallDate'
  scoreCol: 'QualityScore'
  parameters: ['PrepaidPitch', 'ObjectionHandling', ...]
  repo: OutboundRepository

Development Strategy

All 4 processes use USE_MOCK_DATA = true initially. As each DB schema is shared, we flip the repo to live queries one process at a time. No disruption to other processes.

Outbound→ uses Finnable's existing DB (db_external.CallDetails)
Inbound→ mock until schema shared
Chat→ mock until schema shared
Email→ mock until schema shared

  • Branch Manager pages (6)
